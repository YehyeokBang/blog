# 디자인 시스템

## 목적과 범위

이 문서는 개인 기술 블로그 UI를 판단하고 작업하는 공통 진입점이다. 값과 구현을 복제하지 않고, 안정적인 원칙과 선택 기준을 기록한다. 아직 사용하지 않는 패턴은 외부 디자인 시스템에 있다는 이유만으로 프로젝트 규칙이나 구현 대상으로 만들지 않는다.

## 정본과 판단 권한

| 판단 대상 | 정본 |
|---|---|
| 현재 값과 실제 동작 | [`frontend/app/globals.css`](../../frontend/app/globals.css)와 대상 컴포넌트 |
| 디자인 원칙 | 이 문서 |
| 승인된 동작 요구사항 | 관련 OpenSpec |
| 게시글 문체 | [`docs/persona.md`](../persona.md) |

코드와 원칙이 다를 때 문서를 자동으로 코드에 맞추지 않는다. 의도된 변경인지, 구현 누락인지, 오래된 문서인지 먼저 확인한다.

## 디자인 방향

- 깔끔하고 전문적이되 지나치게 무겁지 않은 개발자 블로그를 지향한다.
- 여백과 타이포그래피로 구조를 만들고 장식 요소는 최소화한다.
- 긴 기술 글의 가독성, 모바일 사용성, 명확한 상호작용을 시각적 화려함보다 우선한다.
- mint 계열 accent를 중심으로 쓰며, 과한 shadow와 카드 중첩은 피한다.

## 기초 원칙

### 색상과 상태

색상은 역할을 기준으로 선택하고, 새 색보다 기존 토큰을 우선한다. light/dark 모두에서 대비와 hover·focus·disabled 상태를 확인한다.

### 타이포그래피와 긴 글

제목은 크기와 굵기로 위계를 만들고, 긴 본문은 읽기 편한 줄 길이·줄 높이·문단 간격을 우선한다. 본문, 코드, 보조 정보는 서로 다른 읽기 역할을 명확히 한다.

### 간격과 레이아웃

제한된 간격 스케일과 일관된 정렬을 사용한다. 모바일부터 설계하고, 화면이 넓어져도 콘텐츠의 읽기 흐름이 흐트러지지 않게 한다.

### 상호작용과 접근성

클릭 가능한 대상은 식별 가능해야 하며, 키보드 focus와 접근 가능한 이름을 제공한다. motion preference를 존중하고, 오류·로딩·빈 상태에서 다음 행동을 알 수 있게 한다.

## 현재 사용하는 UI 선택 기준

### 버튼과 아이콘 버튼

주요 행동에는 버튼을 사용하고, 아이콘만 쓰는 버튼은 의미를 알 수 있는 accessible name과 visible focus indicator를 제공한다. 링크 이동은 링크로 유지한다.

### 필터 Chip과 정보 Tag

Chip은 필터처럼 사용자가 상태를 바꾸는 조작에, Tag는 게시글의 분류·메타데이터 표시에 사용한다. 같은 모양이라도 역할을 섞지 않는다.

### 입력과 오류

입력은 무엇을 기대하는지 알려 주고, 오류는 문제와 해결 방법을 가까운 위치에서 명확히 설명한다. 색만으로 오류를 전달하지 않는다.

### 로딩과 피드백

짧은 대기는 불필요한 방해를 피하고, 대기가 길어질수록 진행 상태나 기다리는 이유를 알려 준다. 완료·실패·빈 상태도 사용자가 다음 행동을 판단할 수 있게 한다.

## UI 문구 원칙

버튼, 오류, 빈 상태 같은 제품 UI 문구는 짧고 구체적으로 쓴다. 이 원칙은 게시글 본문의 문체에 적용하지 않으며, 게시글의 목소리는 [`docs/persona.md`](../persona.md)를 따른다.

## 사용자와 디자인을 논의하는 방법

### 현재 모습 → 바꿀 모습 → 사용자 효과

디자인 전문 용어 대신 현재 무엇이 불편한지, 크기·위치·색·간격이 어떻게 바뀌는지, 사용자가 무엇을 더 빨리 찾거나 편하게 쓰는지를 순서대로 설명한다.

### As-is / To-be 비교 기준

크기, 간격, 배치, 색상처럼 시각적 판단이 필요한 경우 로컬 화면이나 스크린샷으로 As-is / To-be를 비교한다. 단순 문구 수정이나 명백한 접근성 보완에는 비교 화면이 필요하지 않을 수 있다.

### 직관적인 피드백을 구체화하는 방법

사용자의 “줄여줘”, “키워줘”, “답답해”, “너무 튀어”, “뭔가 어색해”는 유효한 피드백이다. 각각 글자 크기·요소 너비·내부 여백·요소 간격, 클릭 영역·강조도·콘텐츠 폭, 여백·줄 높이·정보 밀도, 색 대비·굵기·배경·그림자, 정렬·위계·반복·반응형 상태 후보로 번역해 확인한다.

## AI 작업별 읽기 경로

| 작업 | 먼저 읽을 자료 |
|---|---|
| 색상·타이포그래피·간격 변경 | 기초 원칙과 [`globals.css`](../../frontend/app/globals.css) |
| 기존 화면 동작 변경 | 관련 OpenSpec과 대상 컴포넌트 |
| 버튼·필터·입력 UI 추가 | UI 선택 기준과 대상 컴포넌트 |
| 버튼·오류·빈 상태 문구 변경 | UI 문구 원칙과 [`docs/persona.md`](../persona.md) |
| 새로운 UI 패턴 비교 | [SEED 참고 기록](references/seed.md)과 관련 공식 문서 |
| 백엔드 또는 게시글 콘텐츠 작업 | 디자인 문서 생략 |

SEED 참고 기록은 평상시 필독이 아니며, 새로운 UI 패턴을 검토하거나 기존 결정을 재검토할 때만 읽는다.

## 실제 구현 위치

- 디자인 토큰과 전역 스타일: [`frontend/app/globals.css`](../../frontend/app/globals.css)
- 공통 화면 구성과 상호작용: [`frontend/components`](../../frontend/components)
- 페이지별 실제 동작: 대상 `frontend/app` 페이지와 연결된 컴포넌트

## 변경 체크

- 새 값이나 패턴 전에 기존 토큰과 현재 컴포넌트로 해결할 수 있는지 확인한다.
- mobile·desktop, light·dark, keyboard 접근성과 UI 상태를 함께 확인한다.
- 동작 변경은 관련 OpenSpec 요구사항과 실제 구현을 함께 대조한다.
- 필요할 때만 As-is / To-be 비교로 사용자 결정을 돕는다.

## 문서 분할 조건

다음 조건 중 둘 이상이 충족될 때 관련 절을 별도 문서로 분리하는 것을 검토한다.

- 실제 공용 UI primitive가 5개 이상 존재한다.
- 버튼, 입력, 피드백 패턴이 여러 화면에서 반복된다.
- 디자인 진입점이 300줄을 넘거나 한 절이 80줄을 넘는다.
- UI를 지속적으로 변경하는 작업자가 2명 이상이다.
- 문서 충돌이나 잘못된 컴포넌트 선택이 반복된다.
- 코드와 문서의 일치 여부를 자동으로 검사할 수 있다.

독립적인 책임이 생긴 절만 분리하며, 미래 사용을 전제로 빈 문서나 컴포넌트 명세를 만들지 않는다.
