# 디자인 시스템 문서 구조 설계

## 배경

현재 디자인 시스템 문서는 `docs/design.md` 한 파일에 방향, 토큰, 레이아웃, 컴포넌트 동작, 반응형 기준이 함께 들어 있다. 현재 구현을 빠르게 확인하기에는 유용하지만 다음 목적을 함께 충족하기 어렵다.

- 디자인 비전문가인 사용자가 화면의 변화를 직관적으로 이해하고 결정한다.
- AI 에이전트가 UI 작업 전 프로젝트 원칙과 실제 구현을 구분해 읽는다.
- SEED 같은 외부 디자인 시스템에서 무엇을 차용하고 무엇을 채택하지 않았는지 기록한다.
- 실제 코드와 맞아야 하는 사실, 프로젝트가 지향하는 원칙, 외부 참고 자료의 경계를 유지한다.

SEED는 전문 조직이 관리하는 유용한 참고 자료지만 이 프로젝트는 당근 제품이 아니며 SEED React, 토큰, 브랜드 표현과의 호환성을 목표로 하지 않는다. SEED의 결과물을 복제하지 않고 계층적 사고, 역할 기반 토큰, 컴포넌트 선택 기준, 접근성 및 문구 원칙을 프로젝트 맥락에 맞게 재해석한다.

## 목표

- 사람과 AI 에이전트가 함께 사용하는 디자인 문서 진입점을 제공한다.
- 사용자가 디자인 용어를 몰라도 실제 화면 변화와 효과를 기준으로 결정하게 돕는다.
- AI가 작업에 필요한 디자인 지침만 선택해 읽게 한다.
- 외부 참고 자료의 출처, 확인 시점, 차용 여부를 추적한다.
- 현재 프로젝트 규모에 맞는 최소한의 문서 구조를 유지한다.

## 비목표

- SEED React 또는 SEED CSS 토큰을 설치하지 않는다.
- SEED의 정보 구조, 색상, 브랜드 자산, 제품 말투를 복제하지 않는다.
- 이번 문서 재구성에서 UI 코드나 실제 디자인 토큰을 변경하지 않는다.
- 현재 사용하지 않는 SEED 컴포넌트를 미래 요구사항으로 만들지 않는다.
- 별도 디자인 시스템 사이트나 컴포넌트 API 문서를 만들지 않는다.
- 모든 UI 변경에 비교 문서나 스크린샷 생성을 의무화하지 않는다.

## 문서 구조

현재 단계에서는 다음 세 파일만 사용한다.

```text
docs/
├── design.md
└── design-system/
    ├── README.md
    └── references/
        └── seed.md
```

### `docs/design.md`

과거 계획과 완료된 OpenSpec archive 문서의 기존 링크를 보존하는 호환용 안내 문서다. 새 디자인 시스템 진입점인 `design-system/README.md`로 연결한다.

이 파일을 제거하지 않는 이유는 과거 기록을 현재 디렉터리 구조에 맞춰 대량 수정하지 않기 위해서다. 활성 문서와 진행 중 OpenSpec change는 새 진입점을 사용하되 역사 문서의 링크는 그대로 유효하게 유지한다.

### `docs/design-system/README.md`

프로젝트 디자인 작업의 단일 진입점이다. 다음 내용을 한 파일 안의 명확한 절로 구성한다.

1. 범위와 정본 구분
2. 디자인 방향과 기초 원칙
3. 현재 사용하는 컴포넌트의 선택 기준
4. UI 문구 원칙
5. 디자인 협업 방식
6. 작업별 문서 읽기 경로
7. 현재 CSS와 주요 컴포넌트 링크
8. 변경 체크와 향후 문서 분할 조건

현재 색상값, 간격값, 컴포넌트 동작을 문서에 상세히 복제하지 않는다. 실제 값과 동작은 `frontend/app/globals.css`와 대상 컴포넌트를 직접 확인하도록 연결한다. 문서에는 값보다 안정적인 의미와 선택 기준을 남긴다.

현재 존재하는 UI와 향후 후보를 구분한다. 아직 사용하지 않는 패턴은 SEED에 있다는 이유만으로 프로젝트 규칙이나 구현 대상으로 승격하지 않는다.

### `docs/design-system/references/seed.md`

SEED를 외부 참고 자료로 기록한다.

- 공식 사이트와 관련 문서 링크
- 마지막 확인일
- 프로젝트가 차용하는 원칙
- 프로젝트 맥락에 맞게 변형한 원칙
- 채택하지 않은 항목과 이유
- 다시 검토할 조건

이 문서는 SEED 전체의 요약본이나 복제본이 아니다. 평상시 UI 작업의 필독 문서로 지정하지 않으며 SEED 변경을 자동으로 추종하지 않는다. 새로운 UI 문제를 해결하거나 기존 결정을 재검토할 때만 참고한다.

## 디자인 협업 방식

사용자는 디자인 전문 용어보다 실제 화면의 크기, 간격, 색상, 위치와 우선순위 변화로 판단한다. 에이전트는 사용자가 디자인 용어를 알아야만 결정을 내릴 수 있는 방식으로 설명하지 않는다.

### 설명 순서

시각적 변경을 제안할 때 다음 순서로 설명한다.

1. **현재 모습**: 무엇이 불편하거나 어색한지 일상적인 말로 설명한다.
2. **바꿀 모습**: 크기, 위치, 색, 간격이 어떻게 달라지는지 설명한다.
3. **사용자 효과**: 무엇을 더 빨리 찾거나 편하게 사용할 수 있는지 설명한다.
4. **직접 비교**: 시각적 판단에 도움이 될 때 로컬 화면이나 스크린샷으로 As-is와 To-be를 보여준다.
5. **사용자 결정**: 추상적인 유행이나 취향만을 근거로 확정하지 않는다.

예를 들어 “시각적 위계를 낮춘다”로 끝내지 않고 “보조 버튼의 색을 연하게 만들어 글 제목이 먼저 보이게 한다”라고 설명한다. “수직 리듬을 조정한다” 대신 “제목과 본문 사이를 8px 더 벌려 답답함을 줄인다”라고 설명한다.

### 사용자의 표현을 구체화하는 방법

사용자의 직관적인 표현은 유효한 디자인 피드백으로 취급한다. 에이전트가 화면을 조사하고 가능한 원인을 좁힌다.

| 사용자 표현 | 에이전트가 확인할 후보 |
|---|---|
| 줄여줘 | 글자 크기, 요소 너비, 내부 여백, 요소 간격 |
| 키워줘 | 클릭 영역, 글자 크기, 강조도, 콘텐츠 폭 |
| 답답해 | 여백, 줄 높이, 콘텐츠 폭, 정보 밀도 |
| 너무 튀어 | 색 대비, 크기, 굵기, 배경, 그림자 |
| 뭔가 어색해 | 정렬, 위계, 반복, 일관성, 반응형 상태 |

여러 해석이 가능하고 결과가 크게 달라질 때는 후보를 설명하거나 화면으로 비교한다. 작은 가역적 변경은 합리적인 해석을 먼저 제안할 수 있다.

### 비교 자료의 사용

As-is와 To-be 비교는 문서 산출물이 아니라 의사결정 도구다.

- 단순한 문구 수정이나 명백한 접근성 보완에는 비교 화면이 필요하지 않을 수 있다.
- 크기, 간격, 배치, 색상처럼 취향과 시각적 판단이 필요한 변경은 로컬 화면 또는 스크린샷 비교를 우선한다.
- 여러 안이 실질적으로 다를 때만 2~3개를 제시한다. 의미 없는 변형을 늘리지 않는다.
- 확정된 기능·동작 변경만 OpenSpec과 PR에 근거를 기록한다.

## 정본과 판단 권한

디자인 관련 정보는 하나의 직선 우선순위로 판단하지 않고 대상에 따라 정본을 구분한다.

| 판단 대상 | 정본 |
|---|---|
| 현재 색상값, 간격값, 실제 UI 동작 | `frontend/app/globals.css`와 대상 컴포넌트 |
| 프로젝트가 지향하는 디자인 원칙 | `docs/design-system/README.md` |
| 승인된 기능과 동작 요구사항 | 관련 OpenSpec base spec |
| 운영자와 게시글의 목소리 | `docs/persona.md` |
| 외부 근거와 비교 자료 | `references/seed.md` 등 참고 문서 |

코드와 디자인 원칙이 다를 때 문서를 자동으로 코드에 맞추지 않는다. 의도된 변경, 구현 누락, 오래된 문서 중 무엇인지 먼저 판단한다. UI 문구 지침은 버튼, 오류, 빈 상태 같은 제품 문구에 한정하며 게시글 본문의 문체는 `persona.md`를 따른다.

## AI 작업별 읽기 경로

모든 작업에서 디자인 문서를 전부 읽지 않는다.

| 작업 | 먼저 읽을 자료 |
|---|---|
| 색상, 타이포그래피, 간격 변경 | 디자인 진입점의 기초 원칙과 `globals.css` |
| 기존 화면 동작 변경 | 관련 OpenSpec과 대상 컴포넌트 |
| 버튼, 필터, 입력 UI 추가 | 디자인 진입점의 컴포넌트 선택 기준과 대상 컴포넌트 |
| 버튼, 오류, 빈 상태 문구 변경 | 디자인 진입점의 UI 문구 절과 `persona.md` |
| 새로운 UI 패턴 비교 | `references/seed.md`와 관련 공식 문서 |
| 백엔드 또는 게시글 콘텐츠 작업 | 디자인 문서 생략 |

최상위 `AGENTS.md`, `docs/README.md`, `frontend/AGENTS.md`에서 새 진입점과 이 라우팅 원칙을 발견할 수 있게 한다.

## 문서 분할 조건

처음부터 SEED와 같은 상세 계층을 만들지 않는다. 다음 조건 중 둘 이상이 충족될 때 관련 절을 별도 문서로 분리하는 것을 검토한다.

- 실제 공용 UI primitive가 5개 이상 존재한다.
- 버튼, 입력, 피드백 패턴이 여러 화면에서 반복된다.
- 디자인 진입점이 300줄을 넘거나 한 절이 80줄을 넘는다.
- UI를 지속적으로 변경하는 작업자가 2명 이상이다.
- 문서 충돌이나 잘못된 컴포넌트 선택이 반복된다.
- 코드와 문서의 일치 여부를 자동으로 검사할 수 있다.

분리할 때도 실제로 독립적인 책임이 생긴 절만 이동한다. 빈 문서나 미래 사용을 전제로 한 컴포넌트 명세는 만들지 않는다.

## 저장소 연결과 검사

- `docs/README.md`의 활성 디자인 문서는 `docs/design-system/README.md`를 가리킨다.
- 최상위 `AGENTS.md`의 문서 지도도 같은 진입점을 가리킨다.
- `frontend/AGENTS.md`에는 UI 작업 유형별 읽기 경로를 간결하게 추가한다.
- `scripts/check-documentation.mjs`의 활성 문서 경로와 관련 테스트를 새 진입점에 맞게 수정한다.
- 알려진 OpenSpec 인덱스 기준선과 독립된 집중 검증으로 새 진입점의 존재·인덱스 연결, 호환 문서의 비정본 상태, 프론트엔드 두 문서의 라우팅을 검사한다.
- `docs/design.md`는 과거 링크 호환용으로 유지한다.
- 진행 중인 `feed-ui-accessibility`, `mobile-scroll-ux` change의 안정적인 디자인 원칙 링크는 새 진입점으로 옮기고, 승인된 동작은 해당 OpenSpec, 현재 실제 동작은 코드가 권한을 유지한다.
- 새로운 UI 동작을 요구하는 내용은 이번 작업에 포함하지 않는다. 동작 변경은 별도 OpenSpec change로 제안한다.

현재 문서 검사 기준선에는 이번 작업과 무관한 OpenSpec 인덱스 누락 3건이 존재한다. 이번 브랜치에 조용히 섞어 고치지 않는다. 별도 작업에서 기준선을 복구하거나, 이번 변경으로 새 오류가 추가되지 않았음을 구분해 검증한다.

## 검증 기준

작업 완료 시 다음 조건을 만족해야 한다.

- `docs/design-system/README.md`에서 SEED 참고 문서와 실제 구현 정본에 도달할 수 있다.
- `docs/README.md`, 최상위 `AGENTS.md`, 프론트엔드 지침이 새 진입점을 가리킨다.
- 과거 `docs/design.md` 링크가 호환 안내를 통해 계속 유효하다.
- 프로젝트 원칙, 구현 사실, OpenSpec 요구사항, 외부 참고의 권한이 구분되어 있다.
- 디자인 비전문가와의 협업 방식과 As-is / To-be 사용 기준이 명시되어 있다.
- AI 작업별 읽기 경로와 문서 분할 조건이 명시되어 있다.
- SEED 공식 문서 링크, 확인일, 차용·변형·비채택 결정이 기록되어 있다.
- 문서 검사 스크립트와 테스트가 새 활성 문서 경로를 검사한다.
- 알려진 OpenSpec 인덱스 오류가 남아 있어도 디자인 시스템 관련 집중 검사는 독립적으로 통과한다.
- `git diff --check`가 통과한다.
- 전체 문서 검사의 기존 실패와 이번 변경으로 추가된 실패를 구분해 보고한다.

## Git 작업 단위

작업 브랜치는 `docs/design-system-structure`를 사용한다. 문서 구조와 검사 경로만 변경하므로 OpenSpec change를 만들지 않는다. 설계 문서와 실제 재구성은 검토 가능한 의미 단위로 나누어 커밋하며, 커밋과 PR 문구는 영문 Conventional Commit prefix와 한국어 설명을 사용한다.
