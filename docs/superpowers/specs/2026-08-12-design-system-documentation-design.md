# 디자인 시스템 문서 구조 설계

## 배경

현재 디자인 시스템 문서는 `docs/design.md` 한 파일에 방향, 토큰, 레이아웃, 컴포넌트 동작, 반응형 기준이 함께 들어 있다. 현재 구현을 빠르게 확인하기에는 유용하지만 다음 목적을 함께 충족하기 어렵다.

- 사용자에게 디자인 시스템의 계층과 판단 방식을 설명한다.
- AI 에이전트가 UI 작업 전 프로젝트의 원칙과 구현 계약을 구분해 읽게 한다.
- SEED 같은 외부 디자인 시스템에서 무엇을 차용하고 무엇을 채택하지 않았는지 기록한다.
- 실제 코드와 맞아야 하는 정본이 외부 참고 자료에 의해 흐려지지 않게 한다.

SEED는 전문 조직이 관리하는 유용한 참고 자료지만 이 프로젝트는 당근 제품이 아니며 SEED React, 토큰, 브랜드 표현과의 호환성을 목표로 하지 않는다. 따라서 SEED의 결과물을 복제하지 않고 계층적 사고, 역할 기반 토큰, 컴포넌트 선택 기준, 접근성 및 문구 원칙을 프로젝트 맥락에 맞게 재해석한다.

## 목표

- 디자인 문서의 단일 진입점을 제공한다.
- 현재 구현 계약과 앞으로의 판단 원칙을 분리한다.
- 사람과 AI 에이전트가 같은 용어와 읽는 순서를 사용하게 한다.
- 외부 참고 자료의 출처, 확인 시점, 차용 여부를 추적할 수 있게 한다.
- 현재 프로젝트 규모에 맞는 최소한의 문서 계층을 유지한다.

## 비목표

- SEED React 또는 SEED CSS 토큰을 설치하지 않는다.
- SEED의 정보 구조 전체를 복제하지 않는다.
- 당근의 색상, 브랜드 자산, 제품 말투를 모방하지 않는다.
- 이번 문서 재구성에서 UI 코드나 실제 디자인 토큰을 변경하지 않는다.
- 문서마다 컴포넌트 API 명세를 만들거나 별도 디자인 시스템 사이트를 구축하지 않는다.

## 문서 구조

기존 `docs/design.md`를 다음 구조로 재편한다.

```text
docs/design-system/
├── README.md
├── implementation.md
├── foundations.md
├── components.md
├── content.md
└── references/
    └── seed.md
```

### `README.md`

디자인 작업의 단일 진입점이다.

- 이 디자인 시스템의 목적과 범위를 설명한다.
- 사람과 AI 에이전트를 위한 권장 읽기 순서를 제공한다.
- 각 문서의 책임을 짧게 설명한다.
- 정본 우선순위를 명시한다.
- UI 작업 전 확인할 문서와 변경 후 검증할 항목을 안내한다.

### `implementation.md`

현재 배포되는 UI의 구현 계약이다. 기존 `docs/design.md`의 사실성 내용을 이동한다.

- 실제 색상과 타이포그래피 토큰
- 테마와 레이아웃 수치
- 현재 컴포넌트 동작
- 반응형 기준
- 아직 구현되지 않은 항목

값이 충돌할 때 `frontend/app/globals.css`와 실제 컴포넌트를 우선하고 문서를 갱신한다. 이 문서는 외부 참고 자료보다 높은 우선순위를 가진다.

### `foundations.md`

새 UI를 판단할 때 사용하는 기초 원칙을 다룬다.

- 역할 기반 색상과 토큰 명명
- 타이포그래피 위계와 긴 글의 가독성
- 간격, 형태, 레이아웃
- 상호작용 상태와 모션
- 접근성, 터치 영역, 키보드 탐색, 오류 전달

구체적인 현재 값은 반복하지 않고 `implementation.md`로 연결한다. 원칙과 구현값이 섞이지 않게 한다.

### `components.md`

컴포넌트를 언제 선택하고 어떤 위계로 사용하는지 설명한다.

- 주요 버튼과 보조 버튼의 위계
- Button, Chip, Tag의 역할 구분
- Input과 Textarea의 상태 및 오류 표현
- Callout, Snackbar, 빈 상태의 선택 기준
- Skeleton과 Progress 표시의 선택 기준
- Header, navigation, icon-only control의 공통 규칙

현재 존재하지 않는 범용 컴포넌트를 구현된 것처럼 문서화하지 않는다. 필요한 경우 `현재 사용`, `향후 적용 원칙`을 구분한다.

### `content.md`

블로그 UI의 말투와 문구 작성 원칙을 정의한다.

- 명확하고 이해하기 쉬우며 차분하고 친근한 말투
- 익숙한 단어와 능동문 사용
- 버튼은 예측 가능한 사용자 행동으로 작성
- 오류는 문제와 다음 행동을 함께 안내
- 한 문장과 한 UI 요소에는 하나의 목적만 배치
- 버튼·메뉴·라벨과 문장형 메시지의 문장부호 기준

당근 특유의 지역사회 말투나 활기찬 브랜드 표현은 차용하지 않는다. 기술 블로그의 신뢰감과 운영자 개인의 목소리를 우선한다.

### `references/seed.md`

SEED를 외부 참고 자료로 기록한다.

- 공식 사이트와 관련 문서 링크
- 마지막 확인일
- 프로젝트가 차용하는 원칙
- 프로젝트 맥락에 맞게 변형한 원칙
- 채택하지 않은 항목과 이유
- 향후 재검토 조건

이 문서는 SEED 내용을 복제하는 요약본이 아니다. 외부 문서의 변경을 자동 반영하거나 호환성을 약속하지 않는다.

## 정본과 우선순위

디자인 관련 정보가 충돌하면 다음 순서로 판단한다.

1. 실제 UI 코드와 `frontend/app/globals.css`
2. `docs/design-system/implementation.md`
3. `foundations.md`, `components.md`, `content.md`의 프로젝트 원칙
4. `references/seed.md`를 포함한 외부 참고 자료

실제 코드와 `implementation.md`가 다르면 문서를 수정한다. 프로젝트 원칙과 현재 구현이 다르면 버그로 단정하지 않고, 의도된 변경인지 먼저 확인한다. 외부 참고 자료와 프로젝트 원칙이 다르면 프로젝트 원칙을 따른다.

## 저장소 연결

- `docs/README.md`의 활성 문서 항목은 `docs/design-system/README.md`를 가리킨다.
- 최상위 `AGENTS.md`의 문서 지도도 같은 진입점을 가리킨다.
- `frontend/AGENTS.md`에는 기존과 같이 디자인 작업 전 관련 문서를 읽는 규칙을 유지하되 새 진입점과 연결한다.
- 기존 `docs/design.md` 링크는 모두 새 위치로 바꾼 뒤 파일을 제거한다.
- 이미지 `docs/feed.png`, `docs/details.png`는 그대로 유지하고 `implementation.md`에서 상대 경로를 조정해 참조한다.

## 변경 원칙

- 문서 이동 과정에서 현재 구현 계약의 의미를 바꾸지 않는다.
- SEED에서 새로 얻은 원칙은 프로젝트에 맞는 표현으로 작성하고 출처를 남긴다.
- 같은 내용은 한 문서에만 자세히 쓰고 다른 문서에서는 링크한다.
- 현재 구현과 미래 지침을 문장 수준에서 명확히 구분한다.
- 새로운 UI 동작을 요구하는 내용은 이번 작업에 포함하지 않는다. 실제 동작 변경은 별도의 OpenSpec change로 제안한다.

## 검증 기준

작업 완료 시 다음 조건을 만족해야 한다.

- `docs/design-system/README.md`에서 모든 하위 문서에 도달할 수 있다.
- `docs/README.md`, 최상위 `AGENTS.md`, 프론트엔드 지침이 새 진입점을 가리킨다.
- 저장소에 `docs/design.md`를 가리키는 유효하지 않은 링크가 남지 않는다.
- 현재 토큰, 레이아웃, 컴포넌트 동작 정보가 `implementation.md`에서 빠짐없이 유지된다.
- 프로젝트 규칙과 SEED 참고 내용의 우선순위가 명시되어 있다.
- SEED 공식 문서 링크와 확인일이 기록되어 있다.
- `node --test scripts/check-documentation.test.mjs`가 통과한다.
- `node scripts/check-documentation.mjs`가 통과한다.

## Git 작업 단위

작업 브랜치는 `docs/design-system-structure`를 사용한다. 문서 구조 변경은 문서만 수정하므로 OpenSpec change를 만들지 않는다. 설계 문서와 실제 재구성은 검토 가능한 의미 단위로 나누어 커밋하며, 커밋과 PR 문구는 프로젝트 Git 전략에 따라 영문 Conventional Commit prefix와 한국어 설명을 사용한다.
